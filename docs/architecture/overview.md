# Architecture Overview

## Context

`gewu-algorithm` has three fundamentally different responsibilities:

1. deterministic learning and content behavior;
2. optional content generation and analysis;
3. user interaction inside editors or command-line clients.

Keeping these responsibilities separate prevents an editor API or LLM provider from becoming the product's domain model.

All practice modes, including code-oriented typing interactions, are core
capabilities. A client may receive keystrokes, manage focus, and render guidance,
but target selection, assistance state, accepted progress, hint facts,
completion, and scoring remain platform-independent.

## System Shape

```text
                     +----------------------+
                     |   Content Pack(s)    |
                     | AlgorithmUnit files  |
                     +----------+-----------+
                                |
                                v
+-------------+       +---------+----------+       +----------------+
| VS Code     | <---> | Versioned Protocol | <---> | Rust Core      |
| Extension   |       +--------------------+       |                |
+-------------+                                    | Domain         |
                                                   | Templates      |
+-------------+       +--------------------+       | Practice       |
| CLI         | <---> | Direct/Protocol API| <---> | Review         |
+-------------+       +--------------------+       | Persistence    |
                                                   +-------+--------+
+-------------+                                            |
| Future Zed  | <-- compatible adapter when feasible       |
+-------------+                                            v
                                                   +----------------+
                                                   | Optional LLM   |
                                                   | Task Providers |
                                                   +----------------+
```

LLM calls are outside the input and scoring paths. Content generated by an LLM returns to the template validation and review workflow as a draft.

## Planned Workspace

```text
crates/
├── domain/            # IDs, lifecycle, attempts, relations, domain errors
├── template/          # Schema-aware loading, validation, and migration
├── practice/          # Deterministic practice modes and state machines
├── review/            # Platform-independent review and progression policy
├── llm/               # Typed generation tasks and optional provider adapters
├── protocol/          # Versioned client messages and JSON-RPC mapping
├── storage/           # Local attempt and content persistence ports and adapters
└── core/              # Application services that compose domain capabilities

apps/
└── cli/               # CLI commands and stdio protocol host

editors/
├── vscode/            # TypeScript VS Code client
└── zed/               # Future adapter; must not constrain the core
```

Crates should be introduced only when implementation requires them. The directory plan is a boundary map, not a requirement to create empty packages.

Repository directories use short responsibility names because the repository root already provides the `gewu-algorithm` namespace. Published package names, binaries, extension IDs, and other ecosystem-facing identifiers retain an explicit GEWU prefix where needed to avoid collisions. See [ADR 0005](../decisions/0005-directory-naming.md).

### Package and Responsibility Map

| Path | Package or artifact | Primary responsibility |
| --- | --- | --- |
| `crates/domain` | `gewu-domain` | Domain IDs and value objects, content lifecycle, relationships, attempts, and typed domain errors |
| `crates/template` | `gewu-template` | `AlgorithmUnit` parsing, structural and semantic validation, source-file resolution, and schema migration |
| `crates/practice` | `gewu-practice` | Deterministic practice-mode state machines, event transitions, progress facts, hints, and completion rules |
| `crates/review` | `gewu-review` | User review state, scheduling policies, and retention-oriented recommendations; planned for Stage 8 |
| `crates/llm` | `gewu-llm` | Typed generation tasks, task versions, structured-output parsing, and optional provider adapters; planned for Stage 7 |
| `crates/protocol` | `gewu-protocol` | Versioned transport DTOs, handshake contracts, JSON-RPC methods, and domain-boundary conversions |
| `crates/storage` | `gewu-storage` | MVP local attempt and content persistence, atomic writes, migrations, and deletion |
| `crates/core` | `gewu-core` | Application use cases that coordinate domain, templates, practice, protocol-independent persistence, and optional capabilities |
| `apps/cli` | Cargo package `gewu-cli`, binary `gewu` | User-facing CLI, core process lifecycle, and JSON-RPC-over-stdio hosting |
| `editors/vscode` | Extension ID `cnkeysky.gewu-algorithm` | VS Code commands, editor-event translation, decorations, views, process management, and secret storage |
| `editors/zed` | To be decided against the current Zed API | Future adapter with no ownership of domain or scoring behavior |

## Dependency Rules

Allowed direction:

```text
domain <- template
domain <- practice
domain <- review
domain <- storage

domain + template + practice + storage <- core
domain <- protocol mappings <- clients
LLM provider adapters <- LLM task contracts
```

Forbidden dependencies:

- domain or practice depending on VS Code, Zed, Node.js, or web UI types;
- practice depending on an LLM provider;
- protocol DTOs becoming the internal domain model;
- content packs containing executable plugin logic;
- editor clients writing the persistence format directly;
- concrete provider SDK types escaping the provider adapter.

## Processes and Communication

The first VS Code implementation should launch a version-matched native core/CLI process and communicate over JSON-RPC via stdio. This provides process isolation, language-neutral messages, and a reusable CLI test surface.

The extension is responsible for process lifecycle, packaged binary selection, UI, and editor events. The core is responsible for validation, session transitions, scoring, and persistence services.

WebAssembly may be evaluated later for browser-based clients. It is not required for the desktop MVP.

## Data Boundaries

| Data | Default location | Public by default |
| --- | --- | --- |
| Official content pack | Repository or versioned package | Yes, after review |
| User template | Local application data | No |
| Generated draft | Local draft storage | No |
| Practice attempt | Local application data | No |
| API credential | Secret storage | No |
| Protocol log | Local diagnostics with redaction | No |

## Compatibility

Schemas and protocol messages are independently versioned. A client handshake must identify client version, protocol range, and core version before starting a session. Persistent attempts record both the `AlgorithmUnit` revision and practice-engine version needed to interpret a result.
